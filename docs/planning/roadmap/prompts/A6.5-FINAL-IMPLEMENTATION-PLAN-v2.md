1. DEXIE v4

Add this store while restating every v3 store verbatim:

workoutDrafts: '[ownerUserId+slot], ownerUserId, updatedAt'

One accessible row per resolved owner:

{
  ownerUserId,
  slot: 'active',
  draftSchemaVersion: 1,
  createdAt,
  updatedAt,

  workoutIdentity: {
    kind: 'legacy-playbook' | 'cartridge',
    cartridgeId: null | string,
    cartridgeVersion: null | string,
    cartridgeSchemaVersion: null | number,
    dayTemplateKey: string,
    phaseId: null | string,
    hipScore: null | number
  },

  definitionSnapshot: {
    kind: 'legacy-workout-v1' | 'cartridge-day-v1',
    value: {}
  },

  state: {
    kind: 'legacy-hud-v1' | 'cartridge-workout-v1',
    fields: {}
  }
}

Legacy identity uses:

- cartridge fields: null;
- dayTemplateKey: `legacy-day:${day}`;
- phaseId: `legacy-phase:${phase}`.

Cartridge identity uses the real cartridge ID, content version, schema version, `day:${day}` template key and optional phase ID.

`definitionSnapshot` stores the resolved legacy workout or selected cartridge day/phase so an update cannot place old values under changed exercises or prescriptions.

2. DRAFT REPRESENTATIONS

`legacy-hud-v1` stores the existing raw provider state:

- mobChecked, clrChecked;
- strSets, coreSets;
- bagRounds, bagCourse, bagModules, bagWorkouts;
- notes;
- gymSessionType, altRows, altDuration;
- hudScrollY and all five block-open flags.

`cartridge-workout-v1` remains a concrete but temporary form representation:

- itemStateById keyed by prescribed cartridge item ID;
- raw checks, values and per-set values;
- substitutions keyed by prescribed item ID;
- item and session notes;
- custom-session content;
- conditioning progress;
- block-open and scroll state.

These are temporary raw values, not permanent analytics or logging contracts.

3. CONTROLLER OWNERSHIP

`app/src/db/workoutDrafts.js` owns the persistence controller at module scope:

- debounce timer;
- latest pending snapshot;
- monotonic generation;
- serialized promise chain;
- save/error status.

Export:

- `createWorkoutDraftController()` for isolated tests;
- one production `workoutDraftController` singleton.

The module must not access Dexie during module evaluation. Database work occurs only when controller methods are invoked.

`useWorkoutDraftPersistence.js` is a thin React binding that subscribes to controller status and connects it to DBProvider/UI. It does not own timers, generation or the write chain.

This lets `signOut()`, the `SIGNED_OUT` event, `logSession`, discard and conflict preflight synchronously invalidate the same writer.

4. MEANINGFUL INPUT

Implement one pure, tested predicate in `workoutDraftState.js`.

Legacy state is meaningful when any of these exists:

- a checked mobility or cooldown item;
- a non-empty strength value (`kg`, `reps`, `papReps`);
- a non-empty core exercise, sets or reps value;
- any non-empty bag field;
- non-blank notes;
- any custom-session row with non-empty user content;
- non-empty duration.

These never create a draft by themselves:

- day, phase or hip score;
- session-type selection;
- scroll position;
- collapse state.

Once meaningful work exists, all identity, selection and UI fields are saved with it.

Cartridge state is meaningful when any item has a check, raw performed value/set, substitution or note, or the session contains notes/custom-session content. Identity and UI state alone are not meaningful.

5. HYDRATION AND AUTOSAVE

- Resolve the authenticated or validated-offline owner before loading.
- Load only `[ownerUserId, 'active']`.
- Validate owner, schema version, discriminator, identity, snapshot and state.
- Suppress autosave until hydration finishes.
- Do not rewrite the stored row merely because restored/default state rendered.
- A valid draft puts Today into a visible Continue state.
- Continue opens the restored workout and applies saved scroll.
- Create no row until state becomes meaningful.
- Text/numeric changes debounce at 700 ms.
- Checks and substitution choices persist immediately.
- Serialize every write through the controller chain.

Flush pending state on:

- `visibilitychange` when hidden;
- `pagehide`;
- DBProvider unmount;
- before guarded context changes and logging.

The existing NoteEditor precedent covers the 700 ms debounce, serialized writes, immediate discrete actions, visibility flushing and unmount flushing. `pagehide` is a new A6.5 guard.

Promise bounded loss only. Abrupt termination inside the debounce window can still lose the final sub-second edit.

6. STALE-WRITE INVALIDATION

Discard, sign-out and successful logging must:

1. synchronously increment the controller generation;
2. cancel the timer and pending snapshot;
3. serialize behind any already-started write;
4. delete the owner’s active row.

Every scheduled write checks the generation captured when it was queued. A stale save must never recreate a cleared draft.

Save failures preserve in-memory values and display a persistent “Draft not saved” state with Retry.

7. CONTEXT CONFLICTS

All day, phase, hip-score and active-cartridge changes use one draft-aware preflight.

If meaningful live work would move to a different identity:

- Keep workout: cancel the attempted switch.
- Discard and switch: invalidate saves, delete the draft, then apply the change.
- Closing/backdrop: preserve the workout.

There is no “keep this draft and start another” path; A6.5 supports one active draft per owner.

Tab and hub navigation remain unrestricted.

A current legacy draft has null cartridge identity, so cartridge activation does not create a false conflict before A7. Cartridge-bound drafts must conflict with a different cartridge/version. External active-cartridge changes preserve the stored snapshot and enter an explicit conflict state.

Use the existing BottomSheet with large targets and safe-action-first ordering. No new browser prompts or navigation.

8. ATOMIC LOCAL LOGGING

Before logging:

- freeze autosave;
- persist the latest meaningful snapshot so a failed log leaves current recoverable data.

Then run one Dexie transaction across:

- sessions;
- syncQueue;
- workoutDrafts.

Inside the transaction:

1. add the unchanged session row;
2. enqueue the unchanged `{ action, sessionId, payload }` envelope;
3. delete `[ownerUserId, 'active']`.

`enqueueSync()` may join the ambient Dexie transaction; `syncQueue.js` does not need modification.

Only after commit:

- reset in-memory workout state;
- refresh counts and pending status;
- trigger the existing remote queue drain;
- show success.

On failure, all three operations roll back, the draft remains and no success message appears. Remote delivery is not part of the local success boundary.

9. SIGN-OUT AND OWNER ISOLATION

Handle both:

- explicit `signOut()`;
- the Supabase `SIGNED_OUT` event.

Before explicit remote sign-out:

- invalidate the singleton controller synchronously;
- attempt to delete the resolved owner’s draft;
- continue existing cartridge-cache clearing and remote sign-out.

The auth event repeats the local invalidation/deletion idempotently.

A failed local delete must not block sign-out. The composite owner key and validation ensure a later identity cannot hydrate or display the prior owner’s row.

10. INVALID DATA

- Valid supported row: hydrate normally.
- Readable unsupported draft/state version: preserve it and show an explicit update-required state with Discard.
- Malformed/corrupt row: fail closed; never hydrate or overwrite it; show a generic unavailable-draft state.
- Owner mismatch: never hydrate, expose, rewrite or merge it.

The existing dynamic full-backup export includes workoutDrafts automatically.
