## 2. Mission

Turn the Timer hub into a coherent mobile timing instrument that encourages voluntary, repeated use
because it is clear, satisfying, and low-friction.

The finished experience should feel:

- premium, modern, tactical, and subtly futuristic;
- congruent with the accepted Train **Strata + Signal Spine / Execution Strata** language without
  cloning a workout card;
- calmer and more instrument-like than the current bright legacy header bands;
- immediately understandable during a three-second glance;
- tactile through restrained material depth, light, rim reflection, and direct feedback;
- purposeful in both idle and active states;
- fast and reliable on an installed Android PWA and standards-compatible with iOS Safari.

Basic Timer and Custom Rounds should look like two modes of the same product. Each mode has a
different job:

- **Basic** makes starting a stopwatch or a known rest interval nearly effortless.
- **Custom Rounds** helps the user form a clear session prescription, start it confidently, follow
  its phases, and repeat a saved setup later.

This is a real implementation, not a mockup. Keep the existing information architecture and all
functional controls recognizable.

## 6. Ethical behavior-design contract

The developer described wanting a strong psychological association between using the Timer and
training. Implement this only as an ethical, user-controlled habit-support loop:

1. **Stable cue:** give Ready, Running, Paused, phase change, and Complete states a consistent,
   legible visual grammar. Preserve the existing truthful audio/vibration cues.
2. **Low-friction action:** make the existing rest presets, Start/Pause/Resume actions, and saved
   setups obvious thumb-friendly entry paths.
3. **Immediate truthful feedback:** reflect existing timer state instantly through label,
   typography, material state, and one-shot alert feedback.
4. **Repeatable routine:** make an existing saved setup feel like a recognizable one-tap route back
   into a known workout structure.

This direction is informed by habit and physical-activity literature in which prompts/cues,
action planning, self-monitoring, and feedback are common behavior-change techniques. The evidence
is mixed and effects are not magic; do not overclaim causality or describe the UI as hypnosis:

- https://pmc.ncbi.nlm.nih.gov/articles/PMC6305562/
- https://pmc.ncbi.nlm.nih.gov/articles/PMC11161714/
- https://pmc.ncbi.nlm.nih.gov/articles/PMC10498635/
- https://pmc.ncbi.nlm.nih.gov/articles/PMC7429262/

Do not add:

- variable or random rewards;
- points, XP, scores, ranks, streaks, badges, achievements, or confetti;
- fake progress, fabricated readiness/recovery, or unsupported training claims;
- guilt, pressure, urgency, loss-aversion copy, or nagging;
- notifications, reminders, analytics, usage logging, or new stored “habit” data;
- new sound, vibration, haptic, or alarm behavior;
- gamification that competes with safe rest and deliberate training.

The behavioral value must come from cue clarity, action simplicity, and reliable feedback.

## 10. Mobile, accessibility, performance, and offline contract

Design portrait-phone-first for the installed PWA:

- primary timer controls and frequently used presets need at least 48 × 48 CSS-pixel targets;
- no essential hover, drag, long-press, double-tap, or precision gesture;
- no horizontal page scrolling;
- large time values must not clip at narrow Android widths or with large numeric values;
- labels, saved setup names, and controls must wrap or truncate deliberately without overlap;
- preserve safe-area and bottom-navigation clearance;
- preserve numeric keyboard/input behavior;
- retain semantic buttons, labels, field associations, `aria-*`, and focus-visible behavior;
- expose running/paused/phase state in text; never rely on colour or sound alone;
- decorative light, glyphs, and alert layers must be hidden from assistive technology;
- use `aria-live` only if it announces meaningful phase/status changes without reading every tick.
  Never make the clock itself an every-tick live region.

Performance/offline limits:

- no WebGL, canvas, SVG filter system, background video, or new image asset;
- no `backdrop-filter`, blur-heavy filter, or large fixed translucent layer;
- no looping, ambient, decorative, or scroll-driven animation;
- no new animation library or dependency;
- keep shadows static, restrained, and bounded;
- no runtime network request for presentation;
- no new timers/intervals/RAF calls for visual effects;
- retain offline behavior exactly;
- newly refined alert motion must respond to `prefers-reduced-motion: reduce`, leaving a truthful
  static state signal during the existing alert window.
